# Postern: technical notes

The user-facing overview is in [../README.md](../README.md). This file covers how it works and what has been verified.

A small resident app for a Stalwart (JMAP) account. It sits in the tray, gets new-mail push and calendar/task reminders straight from the server, and opens your hosted Bulwark in a webview only while you use it. Closing the window frees the webview completely; the tray process stays at a few MB. Background: [../FEASIBILITY.md](../FEASIBILITY.md) option D.

The log (connection, each push event, each alert and toast; no addresses, names or subjects) goes to stderr with `cargo run` and to `%LOCALAPPDATA%\app.postern\logs\postern.log` (Linux: `~/.local/share/app.postern/logs/postern.log`), which starts over past 1 MB.

## What it does

- **Tray:** an icon with a red dot when the Inbox has unread mail, and a status line in the menu ("3 unread messages", "Offline: …"). Left click opens Bulwark. The menu also has New message, Settings…, Start at login and Quit.
- **Push:** one JMAP EventSource for Email, Mailbox and CalendarAlert (`src/watcher.rs`). It re-arms every 5 minutes so a connection that died silently (sleep, network change) is replaced, and backs off from 5 s to 5 min while the server can't be reached. When the access token is renewed, the new stream is opened before the old one is closed, and a catch-up read covers the swap. A server that keeps refusing fresh tokens (HTTP 401) gets "Sign-in failed" after four tries instead of a retry loop.
- **Mail toasts:** up to 3 per burst for new unread Inbox mail received in the last 24 h, then "N more". Only mail newer than the newest unread mail already seen counts as new, so older unread mail never pops up after you read some. A click opens that message. Changing the notification switches applies at once without reconnecting.
- **Notification sound** (`src/sound.rs`): the sounds Bulwark offers (its `lib/notification-sound.ts`), chosen in Settings. The default, "Same as Bulwark" (`notification_sound` = `bulwark`), follows the sound Bulwark itself is set to; the explicit sounds and Off override it, and Play plays the resolved one. Postern learns Bulwark's choice from the page: the script it runs in the viewer (`init_script`, Bulwark's origin only) reads `localStorage["settings-storage"]` (Bulwark's zustand store: `state.notificationSoundChoice`, `involved` when absent; `state.emailNotificationSound === false` and `state.calendarNotificationSound === false`, Bulwark's switches for the new-mail and the reminder sound; `state.doNotDisturb === true`, a plain boolean, which silences both), shortly after load, every 30 s and when the page is hidden. It works out the sound for mail and for reminders separately, and reports a changed pair through one more IPC command, `viewer_sound_choice({ mail, reminders })`. It is granted like the sign-in commands (run time, the viewer on the configured Bulwark origin only, caller re-checked), takes only `off` or the five ids in each (anything else, and anything unparsable on the page side, is ignored), changes only `bulwark_sound` (mail) and `bulwark_reminder_sound` in config.json, writes only when a value differs and at most once per 5 s (a refused report is sent again at the next check). Both start empty, meaning "not seen yet", for which `involved` (Bulwark's default) is assumed and the settings page says so; the desktop app's own quiet hours (not in that store) are not followed. Played with `rodio` (WASAPI on Windows, ALSA on Linux, which PipeWire and PulseAudio serve) once per burst of new mail and once per reminder, only when the notification is shown, and not while the webmail window is visible (Bulwark plays its own there; a window kept alive hidden counts as closed). Each sound opens the output device on its own thread, plays, and closes it; a sound requested while one plays is dropped, and audio failures are only logged. The MP3s are embedded from `app/sounds` (copied from Bulwark's repository, not under Postern's licence: see its README). `scripts/sync-sounds.sh` refreshes them from upstream, and `--check` only compares; the release workflow runs the check and warns when they differ. The Linux build needs the ALSA headers (`libasound2-dev`, `alsa-lib`).
- **Reminder toasts** (`src/calendar.rs`): Stalwart fires DISPLAY alarms itself and pushes a `CalendarAlert`. The app fetches the event or task title, time and location and shows them, converting the event's time zone to this computer's (floating times are shown as written) and following a moved instance of a recurring event. A click opens the event, or the task list for a task, while Postern is running. These arrive whether or not Bulwark is open, but only while the push connection is up: a reminder that fires while Postern is offline or reconnecting is not shown later.
- **Viewer** (`src/viewer.rs`): your Bulwark instance in a webview window created on demand. Closing the window destroys it, unless "Keep the window in memory after closing" is set to a number of seconds (`keep_viewer_secs`, at most 3600). Only Bulwark's origin and the mail server's load in it; other links open in the default browser, and pop-ups are refused except Bulwark's own `blob:` pages (attachments, print previews). The window's size and position are kept in `window.json`. The webview profile, with Bulwark's cookies, is kept on disk across closes. Sign in once with **"Sign in with your browser"** on Bulwark's login page (see below), or with the form and "Remember me" ticked. Either way Bulwark sets a 30-day cookie that the webview profile keeps across closes; without "Remember me" it is a browser-session cookie, lost every time the window is destroyed.
- **Browser sign-in for Bulwark** (`src/viewer_auth.rs`): Bulwark's login page offers "Sign in with your browser" when it finds its desktop app's bridge (`window.bulwarkDesktop`, version 1). The viewer provides only the sign-in part of it. Bulwark's login opens in your default browser (password manager, passkeys, SSO all work there); Bulwark parks the session on its server and sends a one-time code to a listener on `127.0.0.1/bulwark-desktop/callback`; the page in the viewer redeems it with a PKCE verifier only it holds. The tray sees only that code. The three commands behind it (and the sound report, below) are granted at run time to the viewer on the configured Bulwark origin only, and each checks the caller again. Side effects of the bridge being present: Bulwark treats the window as its desktop app (no browser push sign-up, which the tray replaces anyway, and some "app" wording). The Bulwark admin can turn this off (`desktopBrowserSignIn`). To skip Bulwark's page in the browser and go straight to Stalwart's sign-in (passkeys), turn on "OAuth only" and "Auto SSO" in Bulwark's admin (Authentication); the viewer is kept from auto-redirecting itself, so it still shows the button. Bulwark's session and the tray's are separate sign-ins: each OAuth client has its own rotating refresh token, so they can't share one.
- **Cloudflare Access in your browser** (`src/access.rs`, off unless Settings > "Sign in to Cloudflare Access in my browser" is ticked): when the window's first navigation is redirected to `https://<team>.cloudflareaccess.com/cdn-cgi/access/login/<webmail host>?kid=<audience>…`, that login is not loaded. The hand-off is the one `cloudflared access login` uses (cloudflared `token/transfer.go`, `token/encrypt.go`): an ephemeral NaCl box key pair (`crypto_box`), the default browser opened at `<webmail origin>/cdn-cgi/access/cli?aud=…&token=<public key>&edge_token_transfer=true&send_org_token=true&redirect_url=…`, and a long-poll of `https://login.cloudflareaccess.org/transfer/<public key>` (a request is held about a minute, 404 until the user has signed in; up to ten minutes in all). The answer is base64 of `nonce(24) || box` with the service's key in the `service-public-key` header; it holds the application JWT, which becomes the `CF_Authorization` cookie (host cookie, HttpOnly, Secure, SameSite=Lax, expiring with the token) of the webmail host in the window, and the window loads the webmail. The token stays in memory and is never logged or put in a URL; the team-wide org token in the same answer is dropped unread. While the browser has the user, the window shows a local page with "Sign in in this window instead" (the only IPC, one command, allowed for that local page only: `capabilities/access.json`, the webmail origin can't call it). A failure, a timeout, a cancel, or Access sending the window to login again right after a hand-off falls back to the login in the window, and one flow runs at a time, at most one per 10 s. When the token expires, the next load of the webmail is redirected to login again and the browser (still signed in to Cloudflare there) is used again. Debug builds only: `POSTERN_ACCESS_MOCK=http://localhost:PORT` points the transfer service, the login host and the "browser" at a local mock.
- **Single instance:** a second launch hands its arguments to the running copy. A `mailto:` argument opens Bulwark's composer (`/protocol/mailto?url=…`).
- **Sign-in (OAuth, `src/auth.rs`):** no password is stored or seen. Settings > Sign in reads the server's `/.well-known/oauth-authorization-server`, registers a public client (dynamic registration, loopback redirect `http://127.0.0.1/callback`), and opens your browser at Stalwart's login page. The answer comes back to a one-shot listener on `127.0.0.1` that checks `state`; the code is exchanged with PKCE (S256). Scopes: `openid offline_access` plus JMAP mail and calendars. Only the refresh token is kept, in the OS keyring (Windows Credential Manager, service `postern`, entry `oauth-refresh-token`); Stalwart rotates it on each refresh and the app stores the new one. The access token lives in memory and the push connection is renewed just before it expires. A rejected refresh token shows "Sign-in failed" in the tray. Sign out asks the server to revoke the token (best effort: Settings says whether the server confirmed it) and always forgets it locally. The server's OAuth endpoints, like the URLs in Settings, must use https (plain http is accepted only for this machine). The other settings are in `%APPDATA%\app.postern\config.json`. A 0.1.x install (`dev.bulwark-native.tray`, keyring service `bulwark-native`) is migrated once at start-up (`config::migrate_legacy`), only when Postern has no settings of its own yet; the old token is copied, not moved, but since tokens rotate, the old version has to sign in again after Postern's first refresh. Settings files are written atomically.
- **Isolation:** only the local settings window can call the app's settings commands (`capabilities/settings.json`), under a strict content security policy. Bulwark's pages get only the three browser sign-in commands and the sound report, on Bulwark's origin.

## Server requirements

- Stalwart with JMAP and its built-in OAuth (on by default; open client registration for loopback redirects). No app password is needed.
- For reminders: calendar alarms enabled on the server (web admin: Calendar Alarms > "Enable E-mail Alarms", which despite its name gates all alarms). "Minimum Alarm Interval" is the least time between two alarms of one event: with the default 1 hour, a second reminder on the same event within the hour is skipped. Stalwart skips alarms when they are off, for draft events, and for calendars you're not subscribed to. Only alarms with action DISPLAY are pushed; Stalwart emails EMAIL alarms itself.

## Build and run

```bash
cargo run
```

```bash
cargo build --release
```

Installers, laid out like Bulwark Desktop's releases (NSIS per user and MSI per machine, `Postern-Setup-<v>-<arch>.exe`, `Postern-<v>-<arch>.msi`, a `.sha256` for each). They also add the Start Menu shortcut that notifications need:

```bash
cargo install tauri-cli --version "^2" --locked
```

```powershell
powershell -File scripts/release.ps1 -Arch x64
```

ARM64 needs Visual Studio's "MSVC ARM64 build tools" (the TLS library aws-lc compiles C code); the GitHub workflow builds it on a Windows ARM runner. Icons and installer bitmaps come from `scripts/make-icons.py`, then `cargo tauri icon icons/icon-1024.png -o icons`.

## Linux

- **Packages:** `scripts/release.sh [deb] [rpm] [appimage]` builds for the host architecture into `dist/<version>/`; the Linux bundle settings are in `tauri.linux.conf.json`, which Tauri merges over `tauri.conf.json` on Linux only. Build needs WebKitGTK 4.1 and an appindicator library (ayatana or libappindicator; the package depends on whichever the build machine had, ayatana in CI). The AppImage is about 110 MB because it carries WebKitGTK.
- **Tray** (`src/tray_linux.rs`): Postern's own StatusNotifierItem on the session bus (the `ksni` crate), not Tauri's libappindicator one, which has no click events and so opens the menu on a left click. Left click opens the webmail, right click shows the menu, and the tooltip carries the status. With no StatusNotifierWatcher running it logs once and registers when one appears. GNOME needs its AppIndicator extension, as for any tray icon.
- **Window icon:** on Wayland the app id is GTK's program name, which `main.rs` sets to `Postern` so it matches `Postern.desktop` (deb, rpm, AppImage) and the desktop-entry hint of the notifications; `StartupWMClass=Postern` matches X11's `WM_CLASS`.
- **Notifications** (`src/notify.rs`): XDG notifications with a default action, so a click opens the message or event. Subject and preview are escaped: the notification body is markup to most servers.
- **Web processes** (`src/viewer.rs`): Tauri keeps one WebKit context for the life of the app on Linux, and WebKitGTK left one web process (200 MB and more) behind per window opened. Postern ends a window's web process when the window closes. The shared WebKitNetworkProcess (about 70 MB) stays until Postern quits.
- **Ed25519 guard** (`src/viewer_auth.rs`): WebKitGTK's WebCrypto Ed25519 fails on long messages: from a little under 64 KiB it returns a wrong answer, and at 64 KiB the libgcrypt 1.9 in the AppImage (and on Ubuntu 22.04) aborts the page's process, which left the window blank on every load once Bulwark had a server-managed plugin to verify. The script Postern runs before the page refuses Ed25519 `verify` and `sign` over more than 32 KiB, so Bulwark falls back to its JavaScript verifier. Short messages stay native. The guard is its own script, registered for every frame of the viewer (a plugin's sandboxed iframe included) on any origin, since it only refuses. Workers are not reached: the webview gives them no initialization script, so a verify inside a worker is not covered.
- **AppImage audio:** the AppImage bundles GStreamer's plugins (`bundleMediaFramework` in `tauri.linux.conf.json`). Without them WebKitGTK aborts the page's process as soon as a page plays a sound file (seen 2026-11-14 with Bulwark's new-mail sound). The deb depends on `gstreamer1.0-plugins-base` and `-good` for the same reason; the rpm lists them as weak dependencies (`recommends`, which never block an install), under both the Fedora names (`gstreamer1-plugins-*`) and the openSUSE ones (`gstreamer-plugins-*`) since the names differ; a system that skips weak dependencies and has neither would hit the same abort.
- **AppImage menu entry** (`src/appimage.rs`): on start, an AppImage writes `Postern.desktop` and its icons under `~/.local/share`, only when they differ, and fixes the entry after the file is moved. It never touches a `Postern.desktop` it didn't write (its own carries `X-Postern-AppImage=true`).
- **AppImage self-update** (`src/updates.rs`): Tauri's updater plugin, registered only when running as an AppImage. It reads `latest.json` from the latest published GitHub release a minute after start and then daily, takes only a strictly newer version whose minisign signature matches the public key in `tauri.linux.conf.json` (and whose signed version matches the announced one), and writes it over the AppImage file, so its path, the menu entry and "Start at login" stay valid. Nothing restarts by itself. The download is held in memory while it is checked. Tag builds sign with the `TAURI_SIGNING_PRIVATE_KEY` repository secret; hand-run builds are not signed. Losing that key means existing AppImages can never update again.
- **"Running as an AppImage"** means `APPIMAGE` is set *and* Postern's own executable is inside `APPDIR`. The variables alone are inherited by anything an AppImage starts, and trusting them would let an update overwrite another program's file.

Verified on CachyOS, KDE Plasma 6 on Wayland (2026-11-14): builds with no warnings and tests pass; tray registers and its menu items work (driven over D-Bus); settings and viewer windows open; a second launch reaches the running copy; web processes end within 10 s of closing a window; deb, rpm and AppImage build; the AppImage writes its menu entry once and leaves it alone afterwards; a local signed update was downloaded, installed over the file and restarted into, while a tampered file, a foreign signature, a mismatched version and an equal or older version were all refused.

Not yet verified on Linux: a real sign-in and push against Stalwart; clicking a notification (the request with its action was seen on D-Bus, the click was not); the settings checkbox for updates by eye; GNOME and X11; arm64 and the CI builds on Ubuntu 22.04; an AppImage started through FUSE (tests used extract-and-run); "Start at login" (and it breaks if the AppImage path has spaces, a bug in the autostart library); window position on Wayland (only size is restored).

Without the installed shortcut (NSIS: `Start Menu\Programs\Postern.lnk`; MSI: `Start Menu\Programs\Postern\Postern.lnk`), toasts appear under PowerShell's name (see `src/notify.rs`).

## Status

Verified on Windows 11 with WebView2 157:
- It builds with no warnings; unit tests pass (reminder text and time zones, PKCE against the RFC 7636 vector, the loopback listener rejecting a forged `state`, https-only endpoints, duplicate sign-in parameters, window placement).
- On first run it opens Settings, and the settings page loads its values through IPC.
- A second launch, with or without a `mailto:` argument, reaches the running copy.
- With no Bulwark URL set, opening the viewer brings up Settings instead.
- **Against a real Stalwart (2026-11-11):** connected with the calendars capability present. An event reminder and a task reminder each arrived as a `CalendarAlert` within a second of their time, and both were shown as toasts with Bulwark closed. A new mail was toasted about 1 s after delivery.
- Closing a window takes WebView2 from 6 processes (~150–200 MB private) to 0 within ~4 s, while the app keeps running at ~7.8 MB private (debug build).

- **Installer (2026-11-11):** the x64 NSIS setup (2.4 MB) installed silently per user into `%LOCALAPPDATA%\Postern` with a Start Menu shortcut. On first start it moved the 0.1.x settings and token over and connected to the server, running at 7.8 MB.

Not yet verified:
- the MSI and the ARM64 builds; notifications under the installed shortcut's name;
- renewing the access token mid-session when it expires (renewal at start-up works);
- Cloudflare Access sign-in in the browser on Windows (built and unit-tested; run only on Linux), and what an open page does when the Access session expires mid-use;
- clicking a toast to open the message or event;
- tray menu clicks;
- acknowledging a reminder back to the server (not implemented, so Bulwark may show it again if it's open);
- registering as the system mailto: handler (not implemented);
- macOS; Linux as listed in the Linux section.
